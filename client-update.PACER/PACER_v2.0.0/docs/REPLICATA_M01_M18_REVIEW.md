# REPLICATA M01–M18 — PACER Workflow Review

TAG REPLICATA is a useful case study because the work naturally separated into coherent development areas.

## M01–M02 — architecture correction + operational terminal foundation

The product first had to be re-based from an unacceptable web/dashboard direction into an actual terminal application, then its core operational functions were deepened. These were not meaningful as dozens of independent micro-projects; the architecture and interaction model had to remain coherent across the phase.

## M03–M10 — visual language, topology, motion, whitespace

Multiple successive waves refined one shared terminal grammar: hierarchy, tree rails, focus lineage, backend-driven rename choreography, motion semantics, spatial rhythm, topology and negative space. The value came from **iterating one system repeatedly**, not asking for user sign-off after every glyph or animation primitive.

## M11–M13 — scale, operator trust, continuity

The focus moved from presentation to operational confidence: large-tree legibility, Preview/Apply authority, failure semantics, recovery clarity, and cross-session state. Again, each milestone inherited the full system and developed an integrated capability.

## M14–M16 — hostile filesystem + real target environment

Filesystem authority, Windows filename/collision semantics, crash boundaries, terminal-cell geometry, paste/input and target-host diagnostics were hardening phases. These are appropriate places for stronger qualification because maturity had increased and the work touched destructive/release-critical behavior.

## M17–M18 — performance + scope authorship

Performance removed duplicate authority work; scope authorship upgraded the operator's plan model. Both depended on all prior context and were not independent utilities.

## PACER lessons

1. **The project progressed best in thematic waves.** Each wave could contain many paces without user intervention between them.
2. **Testing was valuable when it supported the wave.** It became harmful when treated as the reason development itself should stop.
3. **Guardrail strictness appropriately increased later.** M14 filesystem hardening deserved stricter gates than M03 visual refinement.
4. **User feedback was most useful at coherent states.** Feedback redirected the next integrated wave instead of approving every small implementation.
5. **Global context mattered continuously.** Visual, operational, filesystem, Windows, performance and scope work repeatedly depended on invariants established many milestones earlier.

This is the behavior PACER v2 formalizes.
